# 写作规范

本文档解释"如何写出有深度的讲解"。规则不多，但每条都直接决定文章质量。

## 写作总纲：具体，不抽象

全文的第一原则。它的含义：

- **用代码说话**：能用代码片段说明的，不写抽象描述。概念性铺垫只做"热身"，正文主体永远是具体代码和具体例子。
- **用具体场景说话**：讲应用时给真实场景（"你点开设置页时"），讲权衡时给具体代价（"多花 N 毫秒"），不给空泛的"更高效""更灵活"。
- **直说结论**：先给结论，再给推导。"React 的 `key` 属性改变时组件会重建"比绕圈子铺垫强得多。
- **把代码讲透**：不追求逐行抠细节，但核心机制和周边的代码（被调用的函数、依赖、相邻模块）必须连成片讲透。读者学完应该能对着一片代码说出每一块在干嘛。

写作时不断问自己：这句话是具体的还是抽象的？如果换成代码、换成数字、换成场景能讲得更清楚，就换。

## 深度讲解的四种武器

### 1. 从"是什么"到"为什么"到"怎么权衡"

浅层的讲解只说"代码做了什么"（是什么）。深度讲解要往下走两层：

- **为什么这样做**：这个设计解决了什么问题？
- **权衡**：代价是什么？什么场景下它是错的？

一个例子：
- 浅："`setState` 会触发重渲染。"
- 深："`setState` 通过不可变更新让 React 能快速比较新旧状态（`Object.is`）来决定是否跳过子组件重渲染；代价是开发者必须手动保证数据不可变，这正是 `immer` 这类库存在的原因。"

讲不清权衡，读者就没法在真实决策中应用知识——而"能自己做决策"正是深度学习的意义。

### 2. 概念金字塔：先给全貌，再逐层下钻

讲解任何机制，先给"金字塔顶"（一张地图：这个机制由哪几部分组成、彼此什么关系），再按依赖顺序逐层下钻。读者随时知道自己在整个图景的哪个位置，不会迷失。

写作格式：先一段"全景"文字（可含简单文字图示/调用链），再分小节深入每一块。

### 3. 具体 > 抽象，例子驱动

抽象概念必须配具体例子。解释机制时，构造一个**最小可运行的心智实验**：

> 假设输入是 `{a: 1}`，第一次调用后 `x` 变成 2，第二次调用后……逐步推演。

这种"逐行走查"是深度文章最珍贵的部分，也是第 4 章"项目代码逐段解读"的核心动作。

### 4. 打通联系：一个概念在不同层的表现

同一个机制，在语言层、框架层、项目层各自长什么样？打通这几层是深度文章的标志。

示例（讲中间件）：Express 的中间件（框架层）→ Node 的 `http` 模块如何收到请求（语言/运行时层）→ 项目中日志中间件的真实代码（项目层）。读者学完能把这个概念"平移"到其他场景。

## 代码讲解的姿态

讲解的核心是"这段代码实际是什么"，不是"这段代码好不好"。

**该做的**：
- 把代码的**实际行为**讲清楚：做什么、怎么做、数据怎么流、与什么交互、调用链怎么走。
- 代码有异常或不寻常之处，如实讲出来（"这段代码会……"），让读者看到代码的真实样子。讲行为，不评价。
- 代码为什么长这样，可讲客观可考的因果：依赖关系、语言/框架特性、历史沿革。

**不该做的**：
- 不唱赞歌：不写"我们精心选择了这个方案""这是一个好设计"。
- 不评判：不写"这段代码很糟糕""这个设计有缺陷""更好的做法是……"。把代码讲透，读者自会判断。
- 不虚构动机：不知道代码为什么这么写，就不要编。讲清实际行为和客观因果就够了。

**为什么这样**：读者要拿文章去定位疑难、做重构演进。只有讲解不带滤镜，他们对代码的把握才准确。

## 代码解读规范

- **完整内嵌**：讲解的代码必须完整贴出，标注来源文件路径。宁可贴多，不要引用行号让人回去查。
- **先全景后细节**：代码长或调用关系复杂时，先用几行伪代码/文字描述整体流程，再进入逐段解读。
- **逐段解读的格式**：每段代码块下方，按代码中的逻辑块解读。引用具体行时写"第 3-5 行"。
- **至少一段"逐行走查"**：给一个具体输入，逐步推演执行过程，展示中间状态变化。
- **删减要声明**：如果原文过长只贴核心段，明确说"省略了 XX 部分，共 N 行"，必要时用注释标注省略处。
- **代码与讲解的比例**：约 1 行代码配 1.5-3 行讲解。光贴代码不讲解，等于没写。

## 面向 vibe coder 的语言

- 用"你"来称呼读者，像聪明的朋友讲解，不是教科书口吻。
- 术语首现给中文 + 英文原名（括号），之后只用中文或英文皆可，保持一致。
- 不用"众所周知""显然"这类词。读者默认零基础。
- 类比服务于直觉建立，但每个类比之后必须回到精确的技术表述，避免类比误导读者的心智模型。
- 讲解"为什么值得学"时给具体场景："当你看到 AI 生成了一段 `useEffect` 依赖数组为空的心智……你能马上意识到它会出什么问题。"
- 涉及性能、并发、内存等主题时，解释清楚"在你项目的规模下是否需要在意"——不要制造焦虑。

## 外部链接规范

- 来源：写作前用 Web 搜索收集，官方文档优先。**禁止编造 URL**，拿不准的链接要核实。
- 数量：≥ 12 个。宁可少而精，不要注水。
- 组织：按"入门 → 进阶 → 权威"或按子主题分组。
- 每个链接配一句话说明：讲什么、适合什么阶段。用户在手机/平板上能直接点开，说明文字用于判断"值不值得现在点开"。
- 覆盖类型尽量多样：官方文档、教程、博客、视频、工具。

## 手机排版细节

- 段落 ≤ 4-5 行；超过就拆。深度靠多段落承载，不靠长段落。
- 善用列表与表格承载"并列信息"（清单、对比、权衡）。
- 标题层级：文章大标题用 `#`，章节用 `##`，小节用 `###`，不超过 `####`。
- 每个章节顶部加 `> 约 X 分钟` 的引用块，标注预计时长（**仅 markdown 版**；`format=html` 时由转换脚本自动估算，不要手写，脚本会清除手动标注）。
- 代码块单行保持可读（超长行手动换行或用拆段规避）。
- **每个代码块最多 50 行**。超过 50 行的代码必须按逻辑拆成多个代码块，段间插入解读。拆分以"逻辑完整"为准——每个拆出的代码块本身自洽、可独立理解，不为凑数硬拆。深度优先，拆分是为了手机纵向阅读。
- 强调用 `**加粗**`，不要滥用斜体。
- 表格列数 ≤ 4，单元格内容短。

## 防止长文走样的自查

写完全文后，对照 SKILL.md 的"质量标准"表逐条检查，并额外问自己：

- 我是在"转述教程"还是"真的懂了在讲"？如果某个概念只是搬运，回去把它真正搞懂再写。
- 每章读者能答出"我学到什么"吗？答不出说明这章没有核心信息。
- 有没有"我知道但不告诉你"的默认知识？有就补进去。
- 文中提到的每一个链接，我是否知道它里面大致讲什么？不知道就去查或删掉。
