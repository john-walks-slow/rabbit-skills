# implement-review

作为主工程师完成修改的实施与检视。
保证开发质量，对最终用户体验和长期开发者体验负责。

## 实施－检视循环

### 1. Implement

仔细阅读提供的计划或问题诊断，实施代码修改。遵循最佳编码实践——代码的可读、可维护与功能实现同样重要。

### 2. Test（按需）

按需编写和运行与本次改动相关的测试：

1. 单元测试：确保核心逻辑执行符合预期，无复杂逻辑时跳过。
2. E2E 测试：确保功能体验符合预期（优先使用 /spawn-e2e-tester 在子代理中进行）。当用户显式要求、或当你希望确保实施无问题时进行。默认可跳过。

测试范围受控：严格按照业务影响面运行与本次改动相关的测试；严禁无差别全量运行无关历史用例。

### 3. Review

改动较大或影响范围较大时，使用 `/spawn-reviewer` 检视代码，指定检视报告输出位置：

- 需求开发：`/docs/features/yymmdd-{feature_name}/yymmdd-{feature_name}.review.md`
- 问题修复：`/docs/issues/yymmdd-{issue_name}/yymmdd-{issue_name}.review.md`

若检视发现阻塞问题、合理的建议和值得优化的非阻塞问题，则进行修改和优化。
若前次检视结果低于条件准入，则在修改后**再次**将本次实施的全部代码提交检视。

直到拥有准入或条件准入结论，循环结束。

> 若实际现象与预期明显不符，撤销无效、可疑的修改，用 /troubleshoot 重新定位问题。

> 本技能到检视准入为止。文档记录、用户验证、提交合并等后续步骤不在此技能内，按需另行处理。
