# workflow-implement-review

作为主工程师完成修改的实施与交付。
保证开发质量，对最终用户体验和长期开发者体验负责。

遵守以下工作流程：

## 1. Implement

仔细阅读提供的计划或问题诊断，实施代码修改。遵循最佳编码实践——代码的可读、可维护与功能实现同样重要。

**当你完成全部计划中的全部实施内容后才进入下一步。**

## 2. Test

测试的目的是确保可能脆弱的部分按照预期工作。只进行必要的、有价值的测试。
请按需进行以下测试：

1. 静态验证：确保项目编译、类型检查（如 `typecheck` / `lint`）全部正常通过。
2. 单元测试（按需）：按照项目规范为核心逻辑编写单元测试。
3. E2E 验收与用例固化（按需）：对于新功能、复杂交互或体验敏感的场景，阅读 `/spawn-e2e-tester` 子代理进行端到端功能/体验测试。必须遵守 /spawn-e2e-tester，禁止在主对话直接进行端到端测试。

测试范围受控：严格按照业务影响面，**仅运行与本次改动相关的模块测试**；严禁无差别全量运行无关历史用例。

**当通过静态验证和测试验收（按需）后才进入下一步。**

## 3. Review

当你的修改大于 150 行，或改动影响范围较大时，必须进行代码检视。

使用 `/spawn-reviewer` 检视代码，指定检视报告输出位置：

- 需求开发：`/docs/features/yymmdd-{feature_name}/yymmdd-{feature_name}.review.md`
- 问题修复：`/docs/issues/yymmdd-{issue_name}/yymmdd-{issue_name}.review.md`

若检视发现阻塞问题、合理的建议和值得优化的非阻塞问题，则进行修改和优化。
若前次检视结果低于条件准入，则在修改后**再次**将本次实施的全部代码提交检视。

**直到拥有准入或条件准入结论后才进入下一步。**

> 当你的修改少于 150 行且代码影响范围可控时，可跳过本步骤。

## 4. Documentation

记录本次工作的背景与结果：

- 需求开发：`/docs/features/yymmdd-{feature_name}/yymmdd-{feature_name}.summary.md`
- 问题修复：`/docs/issues/yymmdd-{issue_name}/yymmdd-{issue_name}.summary.md`

遵循规范按需更新模块级和项目级 AGENTS.md。当且仅当有对后续开发有明确收益的通用经验时，记录到模块 pitfalls 部分。

## 5. Validate

向用户简述本次实现时，除验证文档外，把 `yymmdd-{name}.e2e.md` 中的关键截图内联展示给用户，让用户确认端到端证据。

如果有测试无法覆盖但风险较高，需要用户实机核验的场景，使用 `/update-validation-requirements` 创建或更新用户验证要求文档。（此步骤完全可选，如果测试已经较充分验证、端到端证据充分，则可跳过。）

> 若实际现象与你的预期明显不符，请撤销无效的、可疑的修改，使用 /workflow-troubleshoot 重新定位问题。
> 如果你连续多次修改都未达预期，意味着当前思路不可靠或缺乏关键线索，继续试错只会引入更多不确定性。请清空既有思路从零梳理，不要在错误的路径上反复打转。

## Next Step

用户验证通过后，遵循项目规范提交本次修改的代码和文档。
用户书面同意时，可合并、推送本次提交。
